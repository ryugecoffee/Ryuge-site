# 「今、飲んでほしい珈琲」おすすめ枠（2026-11-22 CEO 確定）

商品一覧の左上（以前「閻魔 禅の深煎り」があった位置）に、常に1商品だけ表示する常設枠です。

| 項目 | ルール |
|---|---|
| 名称 | 「今、飲んでほしい珈琲」／Coffee We Recommend Now／El café que recomendamos ahora |
| 価格 | 常に 100g・税込 1,000円（コードで固定。設定で変えられません） |
| 購入上限 | 1人累計2袋まで。過去のおすすめ商品（以前の掲載商品・禅の深煎り）も合算 |
| 焙煎度 | 固定しない（掲載する豆の焙煎度をそのまま表示） |
| 掲載商品 | `server/featured-coffee.json` の `product` の1行だけで決まる |
| 現在 | グアテマラ ケケスケス（浅煎り） |

## 仕組み

- おすすめ枠の商品は**独立した商品**です。SKU は `enma-featured-<豆>`（今は `enma-featured-quequesques`）。
  価格・在庫（`inventory/enma-featured-…`）・注文・販売履歴は通常商品と別です。
- 掲載中は、元の通常商品（今は `enma-quequesques`）を**一覧に出さず、サーバーでも販売を拒否**します。
  同じ豆を2つの枠・2つの価格で売ることはありません。通常商品の在庫・過去注文はそのまま残ります。
- 購入上限は既存の仕組み（`server/promo.js`。メールアドレスと配送先住所ごとの `promoLedger`）を使います。
  この台帳は商品ではなく**お客様単位**なので、過去・現在のおすすめ商品と禅の深煎りの購入が合算されます。
  在庫と同じトランザクションで確保し、決済失敗・キャンセルで戻ります。通常商品には上限がかかりません。
- おすすめ枠の在庫は定期便に使いません。定期便には通常商品側の在庫が使われます。
- 設定が条件に合わない場合（売り切れ・ロット共有の豆、100g の豆以外、1,000円以外など）は、
  サーバーが起動せず CI も失敗します。誤った価格で販売されることはありません。

関連コード：`server/featured.js`（ルール）、`server/featured-coffee.json`（設定）、`server/catalog.js`、
`src/productData.js`、`server/featured-stock.js`（在庫の移動）、テストは `server/featured-coffee.test.js`。

## 在庫の移動（おすすめ枠 ⇄ 通常商品）

同じ豆の在庫を二重に数えないよう、おすすめ枠の在庫は**新規登録ではなく、通常商品からの移動**で作ります
（初期在庫登録 `initial-stock` ではおすすめ枠の在庫を作れません）。

`POST https://ryuge-site.onrender.com/internal/inventory/featured-transfer`

- 初期在庫登録と同じく、Render に `INVENTORY_ADMIN_TOKEN` がない間は無効（404）です。
  ヘッダー `X-Inventory-Admin-Token` に同じ値を付けます。値は GitHub・チャットに書かないでください。
- 移動できるのは次の2方向だけです。
  - 通常商品 → **いま掲載中**のおすすめ枠（例：`enma-quequesques` → `enma-featured-quequesques`）
  - おすすめ枠（過去の掲載分を含む） → その元の通常商品（売れ残りを戻す）
- 移動できるのは**空き在庫（ready − held）だけ**です。決済中の袋は動きません。2つの在庫は1つのトランザクションで変わるので、合計は変わりません。
- 手順（プレビュー → CEO承認 → 実行）：
  1. プレビュー（何も書き込みません）
     `{"mode":"preview","transfer":{"from":"enma-quequesques","to":"enma-featured-quequesques","quantity":<袋数>}}`
     → 現在の在庫、移動後の在庫、`planHash` が返ります。
  2. CEO がプレビュー内容（袋数）を承認します。
  3. 実行
     `{"mode":"apply","transfer":<同じ内容>,"planHash":"…","expectedProjectId":"<Firebase プロジェクトID>","approval":"<承認者・日時>"}`
     → プレビュー後に在庫が変わっていれば `PLAN_CHANGED` で拒否されます。
     実行すると監査記録 `inventoryTransfers/{planHash}` が残り、同じ内容を再送しても `ALREADY_APPLIED` で何も変わりません。

## PR で承認された在庫移動（管理トークン不要）

最初の在庫移動は、管理トークンを使わずに行えます。移動内容（どの豆を、最大何袋）を
`server/featured-stock.js` の `APPROVED_TRANSFERS` にコードとして書き、PR で確認し、**CEO のマージを承認**とします。
本番反映後、決済サーバーが起動時に1回だけ実行します。

- 実行されるのは、その内容がいまの掲載設定と一致するときだけです。入れ替え後に古い内容が実行されることはありません。
- 移動するのは空き在庫（ready − held）だけで、最大袋数を超えません。決済中の袋は動きません。
- おすすめ枠の在庫がすでにある場合は移動せず、「skipped」として記録します（二重移動防止）。
- 空き在庫が0のときは何も書き込まず、次の起動時にもう一度試します。
- 監査記録 `inventoryTransfers/approved-<id>` が残ります。再起動や複数のサーバーが同時に動いても、移動は1回だけです。
- 2026-11-22 の内容：`enma-quequesques` → `enma-featured-quequesques`、最大15袋（CEO 承認・PR #43）。

決済中だった袋があとで解放されて通常グアテマラ側に戻った場合は、上の管理ルートで移動してください（必要なときだけ）。

## おすすめ商品の入れ替え手順

1. いまのおすすめ枠の売れ残りを元の商品へ戻します（上の「在庫の移動」の逆方向）。
2. `server/featured-coffee.json` の `product` を新しい豆の ID に変え、PR → CI → 承認 → マージします。
   - 掲載できるのは、販売中・100g・ロット共有なしの閻魔の豆だけです（条件に合わないと CI が失敗します）。
   - 価格・名称・上限は自動で引き継がれます。焙煎度は新しい豆のものが表示されます。
   - 元に戻った通常商品は、元の価格（例：ケケスケスなら 1,000円）で通常枠に戻ります。
3. 新しい豆の在庫移動を `APPROVED_TRANSFERS` に1件追加して同じ PR に含めると、マージ後に自動で移動します
   （または、本番反映後に管理ルートで移動します）。
   移動が終わるまで、おすすめ枠は「売り切れ」と表示されます（安全側に倒した動作です）。
