**手順（スタッフ）**
1. Gmail でご依頼のメールを開き、受信日時を確認します。
2. 本人確認

**毎月1日9時より前に届いたご依頼**
- 9時より前に処理できれば、通常どおりその月の請求は発生しません。
- 処理が9時を過ぎ、その月の請求がすでに支払われていた場合は、システムが自動で次のことを行います。
  - その月を「請求しなかった月」として扱います。
  - その月の未発送のお届けを取りやめます（準備中だった豆は在庫に戻します）。
  - その月分の全額を、返金の提案として記録します（CEO 承認待ち）。すでに発送済みのお届けがある場合は、その件数も通知メールに書きます。
- 9時を過ぎていても、その月の請求がまだ確定していない場合（下書き・未払い）は、請求そのものを止めます。返金は不要です。
- 先月の請求日（前月1日9時）より前に届いたご依頼は、この画面では処理できません（`REQUEST_TOO_OLD`）。CEO が個別に対応します。
- 毎月1日の朝は、9時より前に一度受信箱を確認する運用をおすすめします。

**Stripe の画面で直接解約しないでください**

## 1-4. 同時処理の確認（2026-11-20）

エミュレーターテストで一度だけ起きた失敗の原因と、二重請求・在庫の二重減算・発送の二重登録が起きないことの確認です。

- **原因**：同じ契約に関するイベント（申し込み完了と初回の支払い、再送を含め8件）が同時に届くと、Firestore が同じ文書のロック待ちをあきらめ、トランザクションを中止しました（`ABORTED: Transaction lock timeout`、エミュレーターでは `Transaction is invalid or closed` も発生）。
  - 中止されたトランザクションは何も書き込みません。重複は起きていませんでした。
  - ただし、その1件のイベントの処理は失敗し、Webhook は 500 を返していました（Stripe の再送で回復する状態）。
- **対策**：コミットされなかったことが確実なエラーだけを、サーバー内で短い間隔をあけて最大4回やり直すようにしました（`records.retryOnContention`）。対象は次のとおりです。
  - Webhook のイベント処理
  - 確認メールの送信判定
  - 発送管理の操作
  - 解約の記録
  
  それ以外のエラーはやり直しません。Stripe の再送に頼らず、1回の配信で処理が完了します。
- **二重にならない理由**（再送に頼らない仕組み）
  - 請求：定期便で決済が起きるのは、Stripe の Checkout ページ（1つのメールアドレスに1ページ、冪等キーつき、支払いは1回だけ）と、Stripe 自身の毎月の請求だけです。当店のコードは、請求の作成も返金も行いません。回数変更は `proration_behavior: "none"` なので、その場で請求は発生しません。同じ月に2件目の支払いがあった場合は、発送を作らず要確認にします。
  - 発送：発送の記録は固定のID（契約・月・回数）で、トランザクション内で1回だけ作成します（`tx.create`）。
  - 在庫：準備・発送・保留・解約は、操作ごとのIDと発送の状態をトランザクション内で確認してから在庫を動かします。
    - 解約で複数のお届けを同時に取りやめる場合、同じ豆の在庫は1回の書き込みで袋数分を戻します（この点を今回修正しました）。
- **確認したこと**（Firestore エミュレーター）
  - 申し込みイベント12件×8契約を同時に送る処理を160回：エラー0件、確認メールは毎回1通、初回のお届けは毎回1件。
  - 3つのエミュレーターテストを修正後に合計23回実行：すべて成功。
  - メール解約・発送・保留が同時に起きた場合の競合テストを25回実行：すべて成功。在庫は「発送済み」か「戻した」かのどちらか一方になり、二重に動いたことはありません。
- **残る既知の事象**（定期便の外）：Factory の入荷APIで、同じ依頼を6件同時に送ったとき、1件が 503 になることがありました。在庫が動いたのは1回だけです。Factory 側の再送で回復します。変更していません。
